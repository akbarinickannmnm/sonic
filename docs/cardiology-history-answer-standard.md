# SONIC Cardiology History — Phase 2 Answer Standard

## Scope
- 50 cardiology cases remain.
- Exactly 40 shared history questions remain.
- This specification defines how case-specific answers are authored and validated. It does not rewrite all 50 cases or claim medical sign-off.
- The existing UI can continue receiving `CaseHint` strings, but those strings should be rendered from structured authoring records rather than generated by question-number switches over loosely related fields.

## Canonical answer record
Each case should have one explicit record for every stable question ID (`cardio-hist-001` … `cardio-hist-040`):

```ts
type AnswerStatus = "present" | "absent" | "unknown" | "not_applicable" | "mixed";
type HistoryAnswerRecord = {
  questionId: string;           // stable ID from cardiologyQuestionBank
  status: AnswerStatus;         // epistemic/clinical state, not diagnosis
  patientAnswer: string;        // concise, direct Persian, patient voice
  sourceFields: string[];       // exact case-profile facts supporting the answer
  reviewerNote?: string;        // internal only; never shown to learner
};
```

### Status semantics
- `present`: the case explicitly supports the symptom/history/factor.
- `absent`: the case explicitly supports that it is not present.
- `unknown`: the case data do not establish presence or absence. Do not convert this to “no”.
- `not_applicable`: the parent symptom/event is absent, so a detail about that event cannot be answered. Explain this briefly in natural Persian (e.g. «چون درد قفسه سینه ندارم، مدت حمله‌ای برای گفتن نیست.»).
- `mixed`: a compound question has both positive and negative sub-items; enumerate them clearly in patient-friendly wording.

## Writing rules
1. Answer the exact question asked; do not reuse a value merely because it is nearby in the profile.
2. Use concise, direct Persian in first-person patient voice for symptom/history questions. Avoid medical jargon unless the patient would reasonably use it.
3. Never infer an answer solely from the diagnosis label.
4. Do not invent a negative history to fill a gap. Missing data must be `unknown` and rendered as an explicit uncertainty, not “no”.
5. If a parent symptom is absent, dependent details must be `not_applicable`, not populated with another symptom's duration, triggers, quality, or relief.
6. Clinical time-course and onset mode are separate fields. “Started 45 minutes ago” does not imply “gradual”; onset mode must be explicitly supported.
7. For compound questions (past history, medications, risk factors), use `mixed` and report each sub-item that is actually known. Do not dump internal database field names or abbreviations without explanation.
8. Do not reveal the target diagnosis unless the case is explicitly designed as known-disease follow-up rather than diagnostic reasoning.
9. Keep units and numeric values only when documented in the case source. Do not fabricate age, dates, medication doses, smoking pack-years, or family history.
10. Every displayed answer must be consistent with the initial presentation and all other answers in the same case.

## Mandatory cross-answer checks
- Chest pain absent (002) ⇒ 011–019 must not assert a positive chest-pain feature; use `not_applicable` where a detail cannot exist.
- Chest pain absent (002) ⇒ 021 must not say dyspnea accompanies chest pain.
- Palpitations absent (004) ⇒ 027–032 must not describe attacks, rhythm, duration, triggers, or associated symptoms; use `not_applicable` or a clearly qualified independent symptom.
- Syncope/presyncope absent (005) ⇒ 033–034 must not describe a syncopal event, prodrome, or recovery.
- Any dyspnea absent (003) and exertional dyspnea present (022) is a contradiction unless the case explicitly distinguishes a historical episode from current status; otherwise resolve at source.
- Anticoagulant/antiplatelet answer (038) must match the medication record (037).
- The answer to onset mode (009) must be independently documented; never infer it from “X minutes/hours ago”.
- Each record must have nonempty `sourceFields`; `unknown` records may cite the fact that the source profile lacks the data, but must not claim a positive/negative fact.

## Release gates
- 40 unique question IDs per case, in bank order.
- 50 cases total.
- Every answer has status, patientAnswer, and sourceFields.
- Zero unresolved critical contradictions.
- Automated checks do not replace clinical review; the final medical content still requires case-by-case review.
